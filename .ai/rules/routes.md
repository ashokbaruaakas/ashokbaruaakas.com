# Routes

## Portfolio content lives in the database and reaches pages as Laravibe DTOs
Public pages (home, resume, plain-text resume, open source) use controllers in App\Http\Controllers\Portfolio, which get all content from App\Actions\Portfolio\GetPortfolioDataAction. It reads the portfolio tables (profiles, projects, experiences, ...) and returns App\DTOs\Portfolio DTOs as the `portfolio` Inertia prop. Lists are ordered by `sort_order`. App\Http\Middleware\EnsurePortfolioPageIsAvailable runs before `cache.headers` so its responses are never publicly cached: until the portfolio has more than the name and email owner:create starts the profile with (`hasHome`), home renders the `Welcome` page, which shows setup steps while no account exists and otherwise a dashboard link, and other pages return 404; resume and open source also 404 until they have data. Sections and links render only when their data exists. Database\Seeders\AshokBaruaSeeder holds the current owner's content and does nothing once the portfolio has content. It holds one person's data, so it runs by hand only: never add it to deploy workflows, post-deployment.sh, composer setup or DatabaseSeeder. DatabaseSeeder seeds nothing. Database\Seeders\DummySeeder fills an empty install with a fictional owner for local review; its account has a known password, so it refuses to run outside the local and testing environments. Owner images live on the `public` disk, tracked by App\Models\Media and shared as the `media` prop; stored names must include a content hash because nginx serves images as immutable. These pages use `PortfolioLayout`. The owner edits all of this at `/portfolio`: list fields are defined once in App\Enums\PortfolioList and profile fields in Profile::editableFields(), and the validation rules and forms come from those definitions, so add a field there rather than writing a new form. Frontend consumes `resources/types/portfolio.ts`. Public pages run without a session, so they cannot read the signed-in user: PortfolioNav and the `Error` page show their dashboard link from the readable `signed_in` cookie set by App\Listeners\SyncSignedInCookie, and that cookie must never grant access or be set on a public response.
